0.7.4 已有 `custom-tool-*` 一族（8 个载体模块，工作区级自定义工具）。0.8.1 在其上加了**跨工作区共享的全局 Skill**，这是全新的一层：

**扩展层 2 个（401 行）**
- `skill-center.ts`（399）—— UI 编排：选目录、迁移确认、导入确认、权限提示。
- `skill-list-tool.ts`（59）—— **只读的远程发现接口**，给 MCP 客户端列出已装 Skill。

**设计上值得抄的三点**（源码注释原话 "R2 §5.2"）：

1. **导入是事务**：`prepare`（解包+校验+生成预览）→ 用户确认 → `commit`（带 journal）。
   替换同名 Skill 时"旧版本先备份，失败自动恢复"。**包内任何东西都不执行**（`Nothing in the package is executed`）。
2. **原目录永不修改**：切换全局位置时，迁移是"事务复制 + 逐个校验"，旧目录文件完好保留，新目录同名不覆盖。
3. **跨窗口竞态是明确处理过的**：提交前后两次核对 `settings.getDirectory()`，发现另一窗口改了位置就中止并提示，而不是写错地方。

还有两处安全细节：选目录时**拒绝工作区内部和 macOS `.app` 内部**；导入前弹窗明说"Skill 脚本具有当前用户权限，请仅导入信任的来源"。

## 二、链接 / 隧道 / 代理可达性（你问的"链接"）

这是 0.8.1 投入第二多的地方，目标很明确：**让 Bridge 的公网链接在中国大陆的网络环境下能真正连上**。

### 2.1 `extension-host-proxy.mts`（291 → 1 107 行，+816）

单文件涨了 816 行，新增 12 个导出。核心是**自动探测本机代理软件**：

```
CANDIDATE_LOCAL_PROXY_PORTS —— 14 个端口，每个都标了客户端名字
  7890  Clash / Clash for Windows (mixed)
  7897  Clash Verge Rev / Mihomo Party (mixed)
  10809 v2rayN HTTP          10808 v2rayN / sing-box SOCKS5
  2080  sing-box mixed       1080  Shadowsocks SOCKS5
  20809 NekoRay HTTP         20808 NekoRay SOCKS5
  6152  Surge HTTP           6153  Surge SOCKS5
  12450 SakuraCat HTTP       8118  Privoxy
  8888  Fiddler / Charles    8080  标准 HTTP 代理
```

配套：`detectActiveLocalProxyPorts`（并发探活）、`getCachedWorkingProxy`/`setCachedWorkingProxy`（记住哪个能用）、`shouldBypassProxy`、`resolveDeclaredLicenseProxy`。

### 2.2 `cloudflare-edge-relay.ts`（171 行，全新）

解决一个很刁钻的问题，注释原话：**cloudflared 自己不会用 HTTP 代理连边缘节点**。

作者的做法是在本地 `127.0.0.1` 起一个中继，用 `--edge` 把 cloudflared 指过来，然后每条连接用 `CONNECT` 穿过代理送到 Cloudflare 边缘。

```
CLOUDFLARE_EDGE_TARGETS = [
  "region1.v2.argotunnel.com:7844",  "region2.v2.argotunnel.com:7844",
  "198.41.192.7:7844",              "198.41.200.53:7844",   // 代理 DNS misroute 时兜底
]
```

三个细节很见功力：
- **只搬字节，不读内容**——"TLS still terminates at the edge and cloudflared's pinned certificates still decide"。中继不破坏端到端加密。
- **日志只写边缘主机名和代理的回答，绝不写代理地址或凭据**；同一行最多记一次、最多 24 行（cloudflared 会疯狂重试）。
- **区分"代理接受了 CONNECT"和"边缘真的回话了"**：代理可能接受 CONNECT 却没有到 7844 的路由，此时连接会在边缘回应前关闭 —— 这种情况单独给一句人话错误（"代理到 7844 端口的路由多半被封了"）。

### 2.3 `bridge-quick-tunnel.ts`（56 行，全新）

两个坑的修复，注释标为 "0.7.7 follow-up T1/T2"：

- **T1**：不带 `--config` 时 cloudflared 会读 `~/.cloudflared/config.yml`，用户给别的服务写的 ingress 规则会接管 Bridge 地址，**所有请求 404**。修法：Bridge 永远传自己的配置文件。
- **T2**：不带 `--protocol` 时 quick tunnel **只走 QUIC（UDP 7844）且永不回退**。修法：`direct` = `--protocol auto`（QUIC 失败回退 TCP）；`proxy` = `--protocol http2` + 指向本地中继。

路由选择 `auto / direct / proxy` 有记忆：`chooseQuickTunnelRoute` 在"直连失败过"或"代理成功过"时走代理。直连探测超时 45 秒，正常 120 秒。

### 2.4 `bridge-route-token.ts` + `-storage.ts`（65 行，全新）

**"路由身份只有在持久化成功之后才发布"**。用 `initialize`/`rotate` 串行队列 + 跨窗口租约（最多重试 50 次 × 100ms），避免一个慢启动的窗口把另一个窗口的手动重置覆盖掉。

### 2.5 `proxy-bypass.mts`（89 行，全新）

NO_PROXY 规则解析。两个少见但正确的细节：支持 `host:port` 形式；**macOS 系统列表会把 IPv4 网段缩写**（`169.254/16`、`10/8`），缺的字节按 0 补。

### 2.6 `bridge-ngrok-failure.ts`（28 行，载体层新增）

识别 `ERR_NGROK_334` / "endpoint is already online"，区分可重试与不可重试。说明 **ngrok 和 Cloudflare 是两条并行的隧道方案**。

## 三、托管 Bash 终端

0.8.1 给 Bridge 加了 4 个终端工具：`run_command`、`get_command_output`、`cancel_command`、`send_command_input`（见载体 `ide-tool-output.js`）。

- `managed-bash-protocol.ts`（89 行）—— Windows 用 **ConPTY + 产品自带的 PortableGit bash.exe**，一次性 bootstrap 配好私有 PTY 后 `exec` 同一个 bash，后续命令都是原生源码进一个持久交互 shell。注释特意强调 **"No user command is wrapped or evaluated here"**。
  里面有个很具体的坑：`stty -icanon min 1 time 0` —— 不关掉额外的规范模式缓冲，MSYS 的定时 read 会误报 EOF 并把输入留给下一个提示符。
- `bridge-agent-instructions.js`（载体）—— 给模型的契约文字。三平台统一都是 **Bash**（Windows 也是），明令"不要再套一层 `bash -lc`"，并逐平台写明差异（macOS 是 bash 3.2，没有 `mapfile`/`declare -A`；BSD `sed -i` 要备份后缀）。
- `bridge-task-store.js`（256 行，载体层最大的新模块）—— 任务/待办存储，上限 32 任务、8 条历史、终态保留 8 条 / 24 小时 TTL。

## 四、"modern"（2026-07-28）无状态协议世代

`bridge-mcp-modern.ts` 新增 `modernClientIdentity` / `modernTaskOwnerId`，载体新增 `bridge-task-owner.js`。

注释说得很清楚：

> 2025 连接用发起方的 MCP session；**无状态的 2026 请求**改用稳定的"凭据 / 客户端 / 工作区"三元组身份，于是后续请求凭同一身份仍能轮询、送输入、取消。

- `MODERN_COMMAND_OWNER_PREFIX = "modern:"`，`MODERN_TASK_OWNER_PREFIX = "task-modern:"`，身份摘要用 sha256。
- 新增错误码 `COMMAND_NOT_ACCESSIBLE` —— "句柄对该 owner 不可用；**不要绕过作用域，也不要盲目重跑命令**"。
- `timeout_ms` 返回 `status=running` **不杀进程**，继续用 `get_command_output` + `next_offset` 拉。

这是会话亲和（session-affine）与无状态两条请求路径并存的设计，值得单独研究。

## 七、这些能恢复到什么程度

和之前的结论一致，分两层：

| 层 | 状态 |
|----|------|
| 扩展层 33 个新文件 | **作者原始 TypeScript 原件**，含完整注释与类型。上面引的每句注释都是原文。 |
| 载体层 23 个新模块 | **编译产物**，函数名、控制流、错误码、中文文案都在；类型标注、interface、注释永久丢失；`import` 未重新接线，**不可直接运行**。 |

Skills 这条线有点特殊：**UI 编排（`skill-center.ts`）是原件，但 11 个干活的模块全在载体层**，所以 Skills 的算法细节（事务日志怎么写、解包限额具体数值）需要读编译产物才能确认。
