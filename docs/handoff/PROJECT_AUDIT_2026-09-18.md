## 三、我认为判断错了的地方

### 3.1 最重要：`checkPermission` 在原版里是死代码，P1 不是"恢复"，是"新建"

路线图把 P1 写成"可信文件授权**接入**真实构建链"，`check_release_readiness.mjs` 写"Original dispatcher still omits policy"（原调度器仍**省略**了策略）。这个措辞暗示：曾经有过，现在断了，我们去接回来。

**事实不是这样。** 我写了 `tools/audit_permission_producers.mjs` 专门查这件事，区分"消费者"（读取回调）和"生产者"（提供回调）：

```
npm run audit:permission-producers
```

结果：**所有已发布 bundle 和全部重建模块中，生产者数量为 0。**

- `dist/extension.js`：30 处出现，0 处提供
- `runtime/mcp-server.js`：30 处出现，0 处提供
- 5 个 reconstructed 模块：同样 0 处提供

每一个调用点都长这样：

```js
if (context.checkPermission && !await context.checkPermission(path)) { ... }
```

`context.checkPermission` 永远是 `undefined`，`&&` 短路，**检查从不执行**。而 `dispatchFileTool` 只转发 `workspaceRoots` 和 `signal` 两个字段，根本不传 `checkPermission`——这在原始出厂字节里就是如此（`runtime/mcp-server.js` 第 32304 行起可自行查看）。

**这为什么重要：**

1. **没有"原始行为"可对齐。** 前任（和我）花了大量精力纠结"操作类型字段是不是偏离原设计"。这个纠结是多余的——原设计里这条路径压根没跑过，不存在要忠实还原的语义。
2. **0.7.4 真正的文件保护是工作区根包含**（`canonicalizeWorkspaceRoots` + `realpath` + 包含性检查），不是逐文件审批。这一点必须对用户讲清楚，否则用户会以为社区版"弱化"了安全，其实是**增强**了。
3. **`authorization-integration` 门槛的性质变了。** 它不是"重新接线"就能满足的工程任务，而是"要不要给产品加一个原本没有的审批 UI"——**这是产品决策，需要作者拍板，不是助手能替你决定的。**

我没有把这条写成"前任撒谎"。`checkPermission` 这个参数确实存在于原件中，前任标注"原调度器省略了策略"字面上也没错。**错的是由此推导出的优先级**：把一个"从未启用的可选钩子"当成了"待修复的核心回归"，于是它成了唯一的 P1，挡住了其他所有事。

### 3.2 路线图低估了已经到手的材料

三处过于悲观，导致后续任务被无谓地标成 BLOCKED：

**(a) 原始 TypeScript 源码已经在手，不是"需要逆向"的。**
安装器里直接带了 **34 个 `.ts`/`.mts` 源文件**（`recovered/shuncode-extension/src/`，`source-completeness.json` 记录 `all_hashes_match: true`）。这是作者自己的源码原件，不是反编译产物。路线图通篇在讲"重建/候选/推断"，容易让人误以为手上只有编译产物。

**(b) 安装器能在 CI 里完整解包，不是拿不到。**
`installer-forensics.yml` 已经在 ubuntu runner 上 `lfs: true` 拉取 240 MB 原始 EXE、用 innoextract 解出 **9875 个文件 / 1 GB**，退出码 0。`docs/evidence/windows-extraction.json` 就是产物。本沙箱拉不到只是**出口网络限制**（CDN `github-cloud.githubusercontent.com` 被挡，`api.github.com` 通），**不是项目能力限制**。我实测 LFS batch API 返回了合法下载链接，说明对象存在且可授权。

> 复核：`curl -s -u x-access-token:$(gh auth token) -X POST .../info/lfs/objects/batch ...` 返回 href；再 `curl` 该 href 在本沙箱 SSL 失败。

**(c) 载体身份其实已经基本确定，不该继续标"未知"。**
`product.json` 写着 `version 1.132.0`、`nameLong: ShunCode`、`commit 09533f92…`（该 commit **不存在于** microsoft/vscode，证明是作者自建）。Electron 44.2.0 与上游 1.132.0 的 42.7.1 不符——前任据此判定"未确认底座"。

但我查了 1.132–1.138 全部上游 tag，**没有任何一个用 Electron 44.2.0**（最高 42.10.0）。所以结论不该是"我们没认出底座"，而是：**作者在 1.132.0 基础上自行升级了 Electron**。这是"已知的定制点"，不是"未知的身份"。差别很大：前者可以据此去构建，后者只能干等。

### 3.3 最难的判断被排到了最后

`recovered/bridge-ui/bridge-ui-1.js.txt` 有 12 万字节，是从 `workbench.desktop.main.js`（**3677 万字节**）里切出来的一个类。它用的是 `Disposable`、`append`、`$` 这些 **VS Code 内部 API，不是扩展 API**。

这意味着一件很硬的事：**Bridge 主界面无法用扩展形式复现。** 它是编译进 workbench 的内核改动。摆在面前的只有两条路：

- **A：打补丁进 Code OSS 源码树**——能 1:1 还原 UI，但要维护一份 patch set，每次上游升级都要跟。
- **B：用扩展 + Webview 重写界面**——可维护性好得多，但 UI 不会和原版一模一样。

路线图把这个选择放在 P3，却把 P1 设为唯一优先项。**顺序反了。** A 和 B 决定了 P4/P5/P6 全部的工作内容——先定它，后面的任务才有意义；不定它，做多少授权工作都可能白费。

## 四、我建议的计划修订

原则不变：不刷绿门槛、不冒充验收、不动原件。改的是**顺序**和**任务定义**。

### 建议一：把 P1 拆开，并把它从"唯一优先项"降级

现在的 P1 混了两件不同性质的事：

| 拆分后 | 性质 | 建议 |
|---|---|---|
| **P1a 策略模块本身** | 工程任务 | **已完成**。20 项测试、变异验证、伪造计划实测。质量够了。 |
| **P1b 接入真实宿主 + 审批 UI** | **产品决策** | **暂停，等作者决定**。原版没有这个功能，是否要加、长什么样，得你说了算。 |

理由：继续推 P1b 会掉进一个陷阱——为了"接入"而在没有 GUI 验收能力的环境里造一个假宿主，那正是红线禁止的事。

### 建议二：新增 P1.5「载体策略决策」，提到最前面

**这是我认为现在最该做的一件事。** 产出一份对比文档，让作者在 A（补丁 Code OSS）和 B（扩展 + Webview）之间做选择，内容包括：

- 两条路各自能还原多少原版 UI（用已恢复的 85 个方法清单量化）
- 各自的长期维护成本（跟上游升级的代价）
- 各自对 P4/P5/P6 的影响
- 我的倾向性建议及理由

这不需要 GUI、不需要 Windows、不需要网络，**在当前环境完全可做**，而且它解锁的是后面所有阶段。

### 建议三：把"源码构建"从 BLOCKED 改为可试探

现在 `source-built-installer` 标 BLOCKED，理由是依赖 P3–P5。但有个前置问题可以**先在 CI 里验证**、不必等前面全部完成：

> 拿上游 1.132.0 + Electron 44.2.0，在 Windows runner 上能不能 `npm ci` 并编译出可运行的 Code OSS？

这一步失败的话，整个 P6 就要重新设计；成功的话，后面就有了落脚点。**不必等 P3/P4/P5 就能跑**，而且是纯 CI 任务，不需要作者的机器。

### 建议四：给用户的安全说明要改写

必须明确告诉用户：

> 0.7.4 原版**没有**逐文件审批；文件安全依靠工作区根限制。社区版新增的授权策略是**增强**，不是恢复。

否则用户会误以为社区版削弱了原有保护。这条直接关系到你对用户的交代。

### 建议五：`check:release` 的措辞要修正

`authorization-integration` 的 detail 写着 "Original dispatcher still omits policy"，容易读成"原本该有"。建议改为陈述事实：原版从未提供该回调，此门槛衡量的是**新增控制**的验收状态。**门槛状态仍保持 BLOCKED**，只改描述，不改判定。
