# ShunCode 0.8.1 相比 0.7.4 改了什么

你上传了 `ShunCode-0.8.1-Windows-x64.exe`（222 MB）。这份文档回答两件事：
**新版多了什么功能**，以及**新版的代码恢复到了什么程度**。

所有数字都来自机器生成的证据文件，不是我读代码后的印象：

- `docs/evidence/version-diff-0-8-1.json` —— 两个版本逐文件哈希对比
- `docs/evidence/custom-extension-0-8-1.json` —— 从 0.8.1 安装包里取出了哪些文件
- `docs/evidence/installer-0-8-1.json` —— 安装包本身的识别结果

---

## 一句话结论

**0.8.1 是一次大更新，不是修补。** 扩展源码从 34 个文件涨到 68 个，
从 15076 行涨到 21077 行（**+40%**）。没有删除任何文件。

新功能集中在三块：**外部 MCP 接入**（最大，17 个新文件）、
**技能（Skills）系统**（全新）、**网络与代理韧性**（为了在受限网络下还能用）。

你关心的 Bridge、Chat、支付三块都有实质改动，下面分开说。

## 二、新功能逐块说明

### 1. 外部 MCP 接入 —— 本次最大的新增（17 个新文件）

0.7.4 里 MCP 只用于 ShunCode 自己的 Bridge。0.8.1 加了一整套
**连接第三方 MCP 服务器**的能力：

| 新文件 | 作用 |
|---|---|
| `external-mcp-catalog.ts` / `external-mcp-registry.ts` | 服务器目录与登记 |
| `external-mcp-connection.ts` / `external-mcp-network.ts` | 建连与网络层 |
| `external-mcp-oauth.ts` / `-oauth-flow.ts` / `-oauth-commands.ts` | **OAuth 登录授权** |
| `external-mcp-secret-admin.ts` / `-secret-commands.ts` / `-secret-fields.ts` | 密钥的存取与管理 |
| `external-mcp-diagnose.ts` / `external-mcp-status.ts` | 诊断与状态 |
| `external-mcp-stdio-env.ts` / `external-mcp-native-refs.ts` | 本地进程方式的 MCP |
| `external-mcp-preview-token.ts` / `-network-commands.ts` / `external-mcp-center.ts` | 预览、网络命令、管理中心 |
| `mcp-runtime-host.ts` | 检查运行时是否可用、按需拉起 |

新增的用户可见命令：`shuncode.mcp.open`、`.import`、`.preview`、`.retry`、
`.remove`、`.setEnabled`、`.getCatalog`，以及密钥相关的 `.setSecret` /
`.clearSecret` / `.clearAllSecrets` 等。

新增设置：`shuncode.mcp.extraCaCertificates`（企业自签证书场景）。

> **值得注意**：你之前让我评估的 web_agent 项目，优势之一正是"外部 MCP 出站 + OAuth"。
> 0.8.1 说明你在 ShunCode 里已经自己做了这件事。两边的实现可以互相参考。

### 2. 技能（Skills）系统 —— 全新

| 新增 | 内容 |
|---|---|
| `skill-center.ts` | 技能管理中心（导入、启停、换目录、搜索） |
| `skill-list-tool.ts` | 把技能列表作为一个工具暴露给模型 |
| `dist/skill-archive-worker.js` | 技能压缩包的后台解包 worker |
| `media/skills.svg` | 图标 |

新增命令：`shuncode.skills.center`、`.import`、`.refresh`、`.search`、
`.openDirectory`、`.changeLocation`。

技能的底层逻辑放在载体的 `src/` 里（`global-skill-catalog`、`global-skill-import`、
`global-skill-migration`、`global-skill-paths`、`global-skill-settings`、
`skill-archive`、`skill-import-recovery`）—— 见下面第四节的说明。

### 3. 网络与代理韧性 —— 改动密度最高的一块

`extension-host-proxy.mts` 从 11 KB 涨到 **47 KB（4 倍）**，导出从 5 个变成 17 个。
配套 4 个新文件：

| 新文件 | 作用 |
|---|---|
| `proxy-bypass.mts` | 解析 `no_proxy` 规则、识别 PAC 地址 |
| `bridge-payment-network.mts` | 支付请求的独立传输层，含"**下单结果不确定**"错误类型 |
| `bridge-license-network-policy.mts` | 按接口路径分别设定超时与重试预算 |
| `model-endpoint-url.mts` | 模型接口地址的规范化 |
| `cloudflare-edge-relay.ts` | 直连 Cloudflare Argo 边缘节点（`region1/2.v2.argotunnel.com:7844`） |
| `bridge-quick-tunnel.ts` | 隧道走直连还是走代理：`auto` / `direct` / `proxy` |
| `bridge-route-token.ts` / `-storage.ts` | 固定的隧道路由令牌（重启后地址不变） |

新增设置：`shuncode.bridge.cloudflareEdgeRoute`。
新增命令：`shuncode.bridge.license.signInWithGitee`（Gitee 登录提到了一级命令）。

> 这一整块合起来看，是在解决同一个问题：**用户网络受限时，隧道、支付、模型请求都要能走通**。
> `PaymentCreationUncertainError` 这个类型尤其说明问题——作者开始认真处理
> "下单请求发出去了但不知道成没成"这种网络中间态。

### 4. 支付与授权（你说要保留的那部分）

`bridge-license-service.ts` 从 42 KB 涨到 **66 KB**。服务端接口有增有减：

| 端点 | 0.7.4 | 0.8.1 |
|---|---|---|
| `/v1/auth/gitee`、`/v1/auth/gitee/callback`、`/v1/auth/github` | ✓ | ✓ |
| `/v1/licenses/redeem`、`/v1/licenses/refresh` | ✓ | ✓ |
| `/v1/payments/plans`、`/v1/payments/orders`、`/v1/payments/orders/latest` | ✓ | ✓ |
| `/v1/usage/report` | ✓ | **已删除** |

**作者删掉了用量上报。** 对应地，载体里的 `bridge-usage-counter` 模块也不再被引用——
这是 0.8.1 唯一一个"不再使用"的模块。

新增的三个错误类型，说明授权失败的分类做细了：

- `BridgeReauthenticationRequiredError` —— 需要重新登录
- `LicenseHttpError` —— 服务端明确拒绝
- `TransientBridgeLicenseError` —— 临时性故障，不该清掉本地令牌

> 0.7.4 里"被拒绝 vs 连不上"的区分是写在一个函数里的；0.8.1 把它提升成了类型。
> 这个演进对你想移植支付架构到别的项目很有参考价值。

## 三、新版代码恢复到了什么程度

**和 0.7.4 一样好。** 0.8.1 安装包里同样**自带未混淆的 TypeScript 原件**：

- 恢复位置：`recovered/shuncode-0.8.1/`
- 取回 **91 个文件**，其中 `src/` 下 68 个 `.ts`/`.mts`，共 21077 行
- 带完整类型标注、import 路径、注释——就是你当初写的那份，不是反编译出来的

只有 3 个文件没取：`runtime/bin/` 下的 `rg.exe`、`uv.exe`、`uvx.exe`
（第三方可执行文件，不是你的代码）。

### 打包格式：没变，还是 Inno Setup

文件名从 `...-Setup.exe` 变成 `...-Windows-x64.exe`，我一度以为换了打包器，
但证据显示 **0.8.1 仍是 Inno Setup**，`innoextract` 正常解出 10472 个文件
（0.7.4 是 9875 个）。`docs/evidence/installer-0-8-1.json` 里
`extraction_method` 字段记的是 `innoextract`。

第一次跑 CI 失败另有原因，和格式无关：取证工具里写死了 0.7.4 这一个安装包的
大小和哈希，见到第二个包就在 0 秒内拒绝分析。这是个**有意设的防篡改闸门**，
不该为了图快把它拆掉——现在改成了一张登记表，两个安装包各自登记自己的哈希，
不在表上的文件照样拒绝。顺带加的 7-Zip 兜底这次没用上，是为将来真换格式留的。

## 四、一个需要你知道的限制

和 0.7.4 一样，**扩展只是上半层**。0.8.1 的扩展源码引用了 **40 个位于载体
（你那个 Code OSS 分支）`src/` 目录下的模块**，这些模块**没有随安装包发布源码**，
只存在于打包后的 `dist/extension.js` 里。

0.7.4 引用 24 个，0.8.1 引用 40 个，**新增 17 个**：

```
bridge-agent-instructions   bridge-ngrok-failure      bridge-task-owner
bridge-task-store           configure-mcp             explicit-folder-target
external-mcp-import         external-mcp-network-errors
external-mcp-oauth-config   global-skill-catalog      global-skill-import
global-skill-migration      global-skill-paths        global-skill-settings
ide-tool-output             skill-archive             skill-import-recovery
```

不再引用：`bridge-usage-counter`（对应上面说的用量上报被删）。

这意味着：**技能系统和外部 MCP 的核心逻辑，有相当一部分在载体里，不在扩展里。**
要完整重建这两个功能，这 17 个模块需要像之前对 0.7.4 的 41 个 B 层模块那样处理。
好消息是 `dist/extension.js` 也取回来了，里面有它们打包后的实现可供参照。
